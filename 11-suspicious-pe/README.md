# 11 · Suspicious PE: configuration extraction and a YARA rule

| | |
|---|---|
| Open | `KestrelUpdate.exe.i64`, one IDA instance (no Windows needed) |
| Binary | Windows x64 PE, mingw-w64 GCC 16.2, `-O2`, stripped |
| You'll try | malware-style triage, emulating the sample's own decryption routine, indicator extraction, writing and validating a YARA rule |
| Agent time | 3–5 minutes |

## The program

`KestrelUpdate.exe` is an "updater" structured the way an implant often is: an RC4-encrypted configuration (C2 URL, backup URL, sleep and jitter, campaign id, mutex name, autostart registry key) and a host fingerprint. It is a **benign simulation**: it never touches the network, never persists, never writes the registry. It decrypts its configuration and prints a dry-run line. All domains are `*.example`.

`strings` on the file shows no URL at all.

## Before you start

1. Open `KestrelUpdate.exe.i64`, close other IDA instances, open the Assist panel (**Ctrl+Shift+K**), new conversation.
2. If you want the agent to write the YARA rule to disk, set *Write files* to On or Ask; otherwise it stays in the chat.

## Prompt

```
Treat this as a suspicious sample. What is it, what is it hiding, and what is its configuration? Decrypt the configuration by emulating its own decryption routine, list the indicators of compromise, and write a YARA rule for this family.
```

## What to expect

1. Triage: GCC 16.2 (mingw) from the `GCC: (GNU) 16.2.0` banner; imports include `GetComputerNameA` and `GetCurrentProcessId`; strings like `would check in to %s every %s s` and `campaign`.
2. `decompile main` (`0x140002F20`) leads to the decryptor (`0x1400017D0`): the RC4 key schedule and stream are inlined, and the 12-byte key is assembled from immediates on the stack.
3. `emulate_function(0x1400017D0, [{"zero_bytes": 256}], abi: "x64_windows", max_instructions: 100000, memory_writes_limit: 4000)` returns 249 (the plaintext length). The result's `memory_written` section shows the key `kU7!xq9#Lw2$` on the stack and the JSON in the output buffer. The emulator maps the PE from the database and fakes a TEB, so no Windows is involved.
4. The indicators, then `generate_yara` on the decryptor: a byte pattern including the key-building immediates, possibly wildcarded, and validated with `search_signature`.

Reference run (Claude Opus): 35 tool calls, 4 minutes. The configuration was decrypted by emulation and cross-checked in Python, and the YARA rule had five hex strings (the RC4 key schedule with its reciprocal-multiply `% 12`, the stream state layout, the FNV-1a host id, a default immediate, and the config copy with the key wildcarded), each verified to match exactly once. Two extra observations: the RC4 state is not wiped, so a memory dump reveals the C2, and the host id mixes in the PID, which makes it useless across runs.

`tools/gen_config.py` is the script that produced the encrypted blob in `src/config_blob.h`.

## If it gets stuck

* Raise `memory_writes_limit`. With the default the 249-byte output is still shown, but the RC4 swaps flood the trace.
* Only C-runtime imports are modelled by the emulator, not Win32 APIs. The decryptor here is pure, which is typical; API-heavy code needs `call_stubs`.
* The agent may call it malware. Its own banner says "dry run, no network activity"; it is a safe simulation.
* "Emulate 0x1400017D0 with the Windows x64 ABI, a 256-byte zero buffer as the only argument, and a higher memory_writes_limit."
